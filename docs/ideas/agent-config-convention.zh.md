# Agent 配置约定的探索

由于缺少长期项目维护经验，目前对 agent 配置组织方式的判断仍会频繁变化。
先记录想法，通过实际使用积累经验，不急着将其固化为长期约定。

尚未稳定的配置先在本地试行，不提交相关配置文件。这里的想法文档则可以
通过 Git 保留阶段性认识，后续继续修改。

## 简洁的常驻约定

AGENTS.md、skill 与 prompt 使用简洁、明确的表述，删除重复解释和其他组件
已经表达的信息。AGENTS.md 保留稳定规则，skill 与 prompt 指导按需执行的
任务与判断；讨论经过和设计理由留在 idea 与 trace 中。

当前已确定的代码组织规则是：聚合内聚逻辑，布局直观，避免零散拆分；
tests 与 src 的组织对应。

简洁不是单纯减少文件或字数，而是降低理解负担。共同职责可以独立成模块；
配置应保留任务、判断依据与必要边界，将依赖语境的选择留给 agent，不用大量
规则替代判断，也不把每次偏差追加成永久禁令。

Template 用于稳定有实际用途的结构，不应仅因精简而删除。例如 trace 保留
commit hash、关键问题、认识变化与原因，以及记录分隔符，但不固定每次讨论
的小节名称。固定承载方式，保留内容判断。

## 文件语言与修改预览

`docs/` 内使用中文，目录外使用英文，包括 AGENTS.md、skill 与 prompt 模板。
文档服务于用户回顾，配置与工具指导则使用英文组织，不再按 Markdown 文件
类型逐项列举语言例外。

交流和预览说明使用中文，修改预览使用 diff；diff 内的正文遵循目标文件的
语言规则。交流与预览约定放在全局 AGENTS.md，目录语言规则放在仓库配置。

## 从使用经验中提炼 skill

先利用现有能力完成真实任务，再判断哪些工作值得提炼为 skill。不提前固定
尚未验证的流程，但职责已经清楚时，也不必等待整个系统稳定才编写 skill。

[让想法可追溯](traceable-ideas.zh.md) 是一个例子：目前先以自然语言积累
trace，未来可能需要 skill 帮助 agent 更快浏览与维护，但具体职责尚未明确。

Wikipedia 则提供了一个已经明确的 workflow：搜索候选，根据当前问题判断
是否契合，再决定 fetch，最后使用原生工具读取。相关性判断依赖语境，适合
留给 skill；搜索与获取由机械工具完成。

`lookup-wikipedia` 只组织工具使用，不规定论文阅读顺序或笔记模板。完整的
论文阅读 skill 仍需实际体验支撑。

## Skill 命名

Skill 名称优先表达要做什么，而不是只标出涉及的主题或信息来源。Workflow
型 skill 使用简短、明确的动词或动词短语，description 再说明使用时机与边界，
不在名称中罗列整个流程。

例如，`lookup-wikipedia` 比 `wikipedia` 更明确：它表达通过 Wikipedia 查找
参考材料的动作，而不只是标出信息来源。保留来源名称，也避免 `lookup` 过于
宽泛。

这不是所有 skill 都必须以动词开头的格式要求。手册或参考型 skill 可以使用
含义直观的名词，例如 `pi-docs` 已能让人预期它是查阅 Pi 文档的入口。

## 创建 extension 的 skill 规划

后续考虑编写本仓库的 `create-pi-extension` skill。其中一项约束是：根目录
`index.ts` 负责工具声明与注册，核心逻辑放在 `src`。

文件按内聚职责组织，不机械照搬最初给出的划分，也不为每个辅助函数拆文件。
Wikipedia 中独立的 client 模块是一个例子：它聚合两个工具共用的请求逻辑，
使 search 与 fetch 的职责更清楚。

仓库通用的组织规则由 AGENTS.md 承担；skill 按需补充创建 extension 时的
具体指导，避免重复维护相同规则。目前只记录规划，不实现这个 skill。

## 常驻约定与事件上下文

确定的机械动作交给工具，需要语境判断的 workflow 交给 skill；可检测事件
发生时，由 guard 提供相关上下文，不将例行提醒堆入 AGENTS.md。

工具接口贴合实际操作，不为便利而混合多种身份表达。Wikipedia 的搜索结果
直接提供 fetch 所需参数，本地文件路径只作为获取结果，不与网站路径绑定。

对于可以检测的事件，考虑在事件发生时提供相关上下文。例如，提交涉及
`docs/ideas/` 的文档后，需要提醒 agent 更新对应 trace。当前选择通过
Pi extension 的事件机制提供提醒，而不是依赖 Git hook 的输出被 agent
注意到。

提醒型 guard 放在 `.pi/extensions/use-idea-trace/`：

- `index.ts` 检测相关提交，并向 agent 提供上下文。
- `prompt.md` 维护提醒模板与 trace 更新规则。
- 仅在成功产生新 commit，且提交涉及 idea 文档时触发，排除 `.trace/`。
- 提供实际 commit hash、涉及的文档与对应 trace 路径。
- 不阻止操作、不自动生成 trace，也不自动提交。

在首次文档提交的 smoke 中，已观察到 guard 提供了正确的 commit hash 和
同名 trace 路径，随后完成了本地 trace 更新。这验证了当前场景中的提醒链路，
不代表已覆盖其他提交方式或异常情况。

这一选择仍需实际使用积累经验，不是所有机械流程都应使用 extension 的
通用规则。
