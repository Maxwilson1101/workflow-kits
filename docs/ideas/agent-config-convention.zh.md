# Agent 配置约定的探索

由于缺少长期项目维护经验，目前对 agent 配置组织方式的判断仍会频繁变化。
先记录想法，通过实际使用积累经验，不急着将其固化为长期约定。

尚未稳定的配置先在本地试行，不提交相关配置文件。这里的想法文档则可以
通过 Git 保留阶段性认识，后续继续修改。

## 从使用经验中提炼 skill

先利用现有能力完成真实任务，再判断哪些反复出现的工作值得提炼为 skill。
不为了编写 skill 而预先固定尚未验证的流程。

[让想法可追溯](traceable-ideas.zh.md) 是一个实际例子：目前先以自然语言
积累 trace。随着内容增加，可能需要 skill 帮助 agent 更快浏览与维护这些
记录，但现在尚未明确其具体职责，不提前设计。

## 常驻约定与事件上下文

AGENTS.md 保留简短、明确的约定，不将每项机械流程都写成长篇常驻说明。

对于可以检测的事件，考虑在事件发生时提供相关上下文。例如，提交涉及
`docs/ideas/` 的文档后，需要提醒 agent 更新对应 trace。当前选择通过
Pi extension 的事件机制提供提醒，而不是依赖 Git hook 的输出被 agent
注意到。

提醒型 guard 放在 `.pi/extensions/use-idea-trace/`：

- `index.ts` 检测相关提交，并向 agent 提供上下文。
- `prompt.md` 维护提醒模板与 trace 更新规则。
- 仅在成功产生新 commit，且提交涉及 idea 文档时触发，排除 `.trace/`。
- 提供实际 commit hash、涉及的文档与对应 trace 路径。
- 不阻止操作、不自动生成 trace，也不自动提交。

在首次文档提交的 smoke 中，已观察到 guard 提供了正确的 commit hash 和
同名 trace 路径，随后完成了本地 trace 更新。这验证了当前场景中的提醒链路，
不代表已覆盖其他提交方式或异常情况。

这一选择仍需实际使用积累经验，不是所有机械流程都应使用 extension 的
通用规则。
