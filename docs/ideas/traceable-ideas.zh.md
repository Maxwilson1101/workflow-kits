# 让想法可追溯

由于缺少大型系统开发和长期项目维护经验，我希望保留探索中的阶段性判断，
以及促成这些判断的关键经历，逐步形成自己想法的“凸包”。

这里借用数学中的凸包作类比：

- 积累成功经验，逐步扩展 agent 能够可靠完成任务的能力边界。
- 积累尝试与失败的经验，帮助自己作出更好的决策。

追溯不是为了把过去的结论永久固定下来，而是为了在再次遇到类似问题时，
知道当时做了什么、为什么这样做，以及现在是否仍应沿用。

## 当前做法

`docs/ideas/` 的正文记录当前认识，可以随着讨论快速变化。Git 暂时作为
追溯机制的一部分，保存阶段性共识；提交后的自然语言 trace 补充关键问题、
认识变化与取舍原因。

每份 idea 文档对应 `.trace/` 下的同名文档。不同 idea 分别提交，trace
使用 `---` 分隔记录，并通过完整 commit hash 关联实际变更。Trace 内容
暂不纳入 Git。

这一组织方式只是当前采用的简单机制。先使用，出现实际体验矛盾后再调整，
不提前建设完整的知识管理系统。

## 正文与 trace 的分工

正文说明目前希望解决什么问题、采用什么方式，以及哪些问题尚未决定。

Trace 保留形成这些认识的经历，包括尝试、遇到的问题、方向变化与暂时
搁置的想法。它不是完整对话记录，也不只是变更摘要。

过去的判断可能被推翻。保留原因，是为了支持重新判断，而不是把一次经验
直接变成 agent 必须遵守的永久规则。

## 尚未确定的方向

如何检索积累的经历、评估其适用性，以及何时将经验提炼为门禁、skill 或
其他 agent 配置，仍需实际使用经验，不在当前阶段设计。
